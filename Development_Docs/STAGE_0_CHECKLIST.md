# DocuVerse 0단계 결정·기술 후보·검증 체크리스트

[통합 로드맵](ROADMAP.md)의 0단계에서 작성할 결정과 1~2단계에서 실행할 검증을 연결한다. 체크리스트를 작성했다는 사실은 구현·성능·호환 검증 완료를 의미하지 않는다. 초기 기술 선택은 프로토타입을 위한 가설로 기록하고 실제 결과를 확인한 뒤 확정한다.

## 1. 사용 방법과 완료 범위

- `[x]`는 해당 항목의 결정·산출물 또는 실제 검증 근거가 준비된 경우에만 표시한다.
- 0단계에서는 초기 범위·대표 문서·잠정 구조·비교 후보·검증 절차·테스트 환경 확보 계획을 정한다.
- 1~2단계의 실제 입력·저장·표시 검증은 별도 미완료 항목으로 남긴다. 이를 모두 끝내야 최소 코어 구현을 시작할 수 있는 것은 아니다.
- 각 결정에 `잠정 선택 / 비교 후보 / 선택 이유 / 재검토 조건 / 확인할 단계`를 남긴다. 버전·결과·영상이 없는 환경을 지원 완료로 표시하지 않는다.
- 기능·호환·심사 규칙은 [공통 문서](README.md)와 [실행 모드·플러그인 정책](Framework/1.%20framework-runtime-and-plugin-policy.md)을 따른다.

## 2. 이미 합의된 방향

아래 체크는 제품 방향에 대한 합의이며 구현 완료 표시가 아니다.

- [x] 독립 에디터, 공식 태블릿 앱, 셀프호스팅 프레임워크·라이브러리로 제품을 구분한다.
- [x] 앱은 iPadOS·Android 태블릿을 우선 대상으로 하고 Windows·macOS 앱은 미정으로 둔다.
- [x] 공통 문서·로직을 공유하고 입력·UI·저장·인증은 호스트·어댑터에서 처리한다.
- [x] 사이트 첫 구동 시 동적 ON/OFF를 선택한다. OFF에서는 정적 기능·정적 대체만 제공한다.
- [x] 앱 로컬 편집·저장·필기를 사이트의 동적 스위치에 종속시키지 않는다.
- [x] 일부 플러그인만 환경별로 재사용하고 실제 테스트·영상·심사를 거친 범위에 호환 태그를 부여한다.
- [x] 계정·클라우드·협업·마켓플레이스를 초기 로컬 앱·정적 사이트의 필수 조건으로 두지 않는다.

## 3. 구현 전에 먼저 정할 결정

### D01. 첫 사용 흐름과 범위

- [ ] 첫 검증 목표를 `태블릿 작성 → 로컬 저장 → 재시작·재열기 → 내보내기 → 웹 표시`로 기록한다.
- [ ] 프로토타입에 포함할 문단·제목·목록·서식·이미지·첨부 참조·기본 필기·도형 범위를 정한다.
- [ ] 필기는 문서 안의 블록인지, 자유 배치 영역인지 등 첫 편집 범위를 정한다. 무한 캔버스·고급 인식까지 초기 필수로 확대하지 않는다.
- [ ] 필수 서식·필기 조작과 후속 항목을 나눈다. 예: 선 그리기·색상·지우기·실행 취소 우선, 고급 인식 후속.
- [ ] 나무위키 전체 문법·고급 수식·실시간 협업·광범위한 API 연동을 초기 검증에서 제외하거나 필요한 최소 예외만 기록한다.
- [ ] 첫 태블릿 검증 순서를 정하고, 다른 우선 태블릿 환경을 언제 확인할지도 기록한다.

### D02. 공통 문서와 원본 보존

- [ ] 문서 ID·블록 ID·스키마 버전·첨부 참조·확장 데이터의 최소 규약을 정한다.
- [ ] 편집 엔진의 문서를 원본으로 삼을지, 별도 공통 문서에 엔진 데이터를 연결할지 비교한다.
- [ ] 텍스트·필기·도형이 같은 문서에서 연결되는 방법과 좌표·크기·색상 등 필수 데이터를 정한다.
- [ ] 미지원 블록은 원본 데이터를 유지한 대체 블록으로 표현하는 등 명시적인 보존 경로를 정한다. 엔진 파싱 시 자동으로 보존된다고 가정하지 않는다.
- [ ] 원본 저장과 Markdown·HTML 등 호환용 내보내기를 구분하고 변환 손실의 안내 방식을 정한다.
- [ ] 문서 편집 history와 디스크 저장·백업 이력의 책임을 구분한다.
- [ ] 변경된 스키마를 읽을 수 없을 때의 동작을 정한다. 초기에는 읽기 제한·원본 보존 등 최소 정책부터 가능하다.

### D03. 저장·복원 경계

- [ ] 첫 로컬 저장을 문서 JSON·첨부 파일 등 단순한 형태로 시작할지 결정한다.
- [ ] 파일·폴더·첨부 참조의 이동과 내보내기 묶음 구조를 정한다. 인덱스용 DB 선택과 문서 원본 형식은 구분한다.
- [ ] 저장 완료 시점·중단·재시작·쓰기 실패 시 유지할 원본과 사용자 안내를 정한다.
- [ ] 앱 전용 저장 영역과 외부 파일 제공자 연결의 초기 범위를 구분한다. 외부 클라우드 연결은 검증 후 확대한다.
- [ ] 서버·계정 없이 저장·재열기·명시적 내보내기가 가능한 구조인지 확인할 절차를 정한다.

### D04. 모듈·개발 환경

- [ ] 코어·포맷 변환·편집 어댑터·읽기 전용 렌더러·앱 호스트·사이트 빌드의 경계를 그린다.
- [ ] 최초 구현에서 사용할 언어·편집 후보와 후보별 연결 지점을 잠정 선택한다.
- [ ] 첫 웹 UI 어댑터는 필요 범위만 선택한다. React·Vue·Svelte를 모두 구현하는 계획으로 시작하지 않는다.
- [ ] 코드 공유 범위에 따라 단일 저장소의 논리 모듈 또는 workspace 패키지 구성을 잠정 선택한다. 정식 공개 패키지 이름은 뒤로 미룰 수 있다.
- [ ] 패키지 관리자·타입 검사·빌드·테스트 도구를 각각 최소 구성으로 정하고 실제 선택 버전을 기록한다. 기존 TypeScript·Rollup·Jest 구상은 비교 출발점이다.
- [ ] 개발·빌드·실기기 설치를 재현할 최소 명령과 필요한 개발 장비를 기록할 위치를 정한다.

## 4. 비교할 기술 후보

아래 후보는 공식 문서에서 구조를 확인한 비교 대상이다. DocuVerse 적합성·성능·호환은 아직 검증하지 않았다. 공식 문서 확인일은 2026-10-24이며 실제 실험에서는 정확한 버전·운영체제·런타임을 별도로 기록한다.

### T01. 편집 엔진과 공통 문서

- [ ] 임의 HTML·알 수 없는 노드·확장 데이터를 가져올 때 제거되는 정보가 있는지 확인하도록 한다.
- [ ] 초기에는 한 후보부터 연결하고 유지 불가능한 문제나 비교 필요성이 확인되면 대안을 실험한다. 두 편집기를 제품 수준으로 동시에 구현하지 않는다.

### T02. 태블릿 앱의 구성

| 후보 | 비교하려는 구성 | 확인할 점 |
| --- | --- | --- |

마지막 후보는 웹 편집기의 네이티브 자동 변환이 아니다. 네이티브 영역을 늘릴수록 입력·선택·history·표시를 어떻게 연결할지 별도 검증이 필요하다.

- [ ] 먼저 실험할 셸 구성을 하나 고르고 전환 조건을 정한다. 예: 필요한 IME·펜 동작을 해결할 수 없을 때 재검토.
- [ ] WebView·Capacitor·네이티브 영역은 조합 가능하다는 점을 반영해 셸 선택과 필기 선택을 분리한다.
- [ ] iPadOS 빌드·설치에 사용할 개발 장비·도구 접근 계획과 Android 개발·설치 환경을 기록한다.

공식 입력 도구 후보: [Apple PencilKit](https://developer.apple.com/documentation/pencilkit), [Android Ink API](https://developer.android.com/develop/ui/compose/touch-input/stylus-input/about-ink-api). 후보 도구가 공통 필기 형식이나 상호 편집 호환을 보장하는 것은 아니다.

- [ ] 스트로크 원본, 플랫폼 전용 원본, 표시용 이미지 중 무엇을 저장·내보낼지 잠정 선택한다.
- [ ] 다른 환경에서 조회만 가능한 경우와 계속 편집 가능한 경우를 구분한다.
- [ ] 확대·축소·화면 회전·재열기 후 좌표·색상·크기가 유지되는지 검증하도록 한다.

- [ ] 단계 2는 사이트 전체보다 공통 문서의 HTML·기본 웹 표시를 먼저 검증하도록 정한다.
- [ ] 엔진 연계 정적 렌더러와 직접 관리하는 블록 렌더러의 비교 범위를 정한다. 커스텀·미지원 블록과 필기 표시를 포함한다.
- [ ] 최종 사이트 기반은 잠정 선택하되 단계 2의 렌더러 검증 후 재검토할 수 있게 한다.
- [ ] 동적 OFF를 빌드 구성으로 적용할지, 서버 배포에도 실행 설정을 둘지 정한다. 필요 시 재빌드·재배포·재시작 절차를 명시한다.
- [ ] 프레임워크의 렌더링 모드 전환이 DocuVerse의 플러그인·백그라운드 작업 중단까지 자동 보장한다고 가정하지 않는다.

### 비교의 범위 제한

- [ ] 편집 엔진과 앱 셸은 대표 후보부터, 필기는 웹 입력과 필요한 네이티브 입력부터 비교한다.
- [ ] 새 후보를 추가할 때는 기존 후보로 해결되지 않는 문제와 비교 종료 조건을 기록한다.
- [ ] 라이브러리 버전·패키지 경계·배포 조건·필요 기능의 이용 조건을 확인할 항목을 남긴다. 이번 문서에서 라이선스를 변경하거나 전체 배포 정책을 확정하지 않는다.

## 5. 대표 문서와 비교 자료

### 기능 문서

- [ ] 한글·영문·숫자·이모지·복합 입력을 포함한 기본 텍스트 문서를 정의한다.
- [ ] 제목·목록·링크·기본 서식·간단한 표를 포함할 범위를 정한다.
- [ ] 이미지·첨부 파일을 문서 데이터와 분리 참조하고 누락·이동 사례를 정의한다.
- [ ] 기본 필기·도형과 미지원 확장 블록을 같은 문서에 넣는 사례를 정의한다.
- [ ] 원본·정상 표시·내보내기 결과·변환 손실을 비교할 기준을 정한다.

### 규모별 문서 초안

아래 수치는 부하 자료를 만들기 위한 제안이며 지원 한도·최소 사양·달성한 성능이 아니다. 0단계에서 실제 사용할 수치를 정하고 1~2단계에서 동일 자료로 측정한다.

| 자료 | 텍스트·블록 초안 | 미디어·필기 조건 |
| --- | --- | --- |
| 소형 | 약 1천 자·20블록 | 이미지 1개·짧은 필기 |
| 일반 | 약 1만 자·200블록 | 이미지 10개·반복 필기 |
| 부하 | 약 10만 자·2천 블록 | 미디어·스트로크 수를 별도로 늘려 측정 |

- [ ] 글자 수·블록 수·이미지 해상도·첨부 총용량·스트로크/점 수를 각각 기록한다.
- [ ] 같은 원본·같은 입력 순서로 비교할 수 있도록 자료와 재현 절차의 버전을 관리한다.
- [ ] 부하 문서는 초기 데이터 흐름이 작동한 뒤 실행한다. 작은 문서의 입력·보존 실패를 성능 튜닝으로 덮지 않는다.

## 6. 검증 계획: 0단계에서 정의하고 이후 실행

아래 표는 이후 단계에서 실행할 검증 목록이며 현재 결과는 모두 미실행이다. 이 절의 체크박스는 0단계의 계획 준비 여부를 표시한다. 실제 검증 통과와는 구분하여, 각 행의 재현 절차·기대 결과·기기·측정 방법을 먼저 준비한다.

| ID | 확인할 항목 | 정상 판단 기준 | 실행 시점 |
| --- | --- | --- | --- |
| V01 | 문서 생성·변경·직렬화·재열기 | 지원 데이터와 미지원 확장 원본이 보존됨 | 1단계 |
| V02 | 서버·DOM·UI 의존성 | 코어 문서 로직을 편집 UI·동적 서버 없이 실행 | 1~2단계 |
| V03 | 한글 IME·선택·입력 | 조합 중 중복·누락, 커서 이동·붙여넣기·undo 오류 없음 | 2단계 |
| V04 | 펜·손가락·스크롤 | 정의한 필기·지우기·선택·스크롤 동작과 좌표 복원 | 2단계 |
| V05 | 로컬 저장·복원 | 저장 완료한 문서가 중단·재시작 후 복원, 실패 시 기존 원본 유지 | 1~2단계 |
| V06 | 첨부·경로·권한 | 이동·누락·접근 해제에 대한 처리, 원본 문서 손상 없음 | 2단계 이후 |
| V07 | 웹 읽기 전용 표시 | 편집 UI 없이 지원 블록·필기 표시, 미지원 블록 대체 | 2단계 |
| V08 | 앱 → 파일 → 웹 | 명시적 내보내기·가져오기, 원본·참조·변환 손실 확인 | 2단계 |
| V09 | 모드 선택·유지 | 첫 구동 선택 저장, 재시작·재빌드 등 적용 절차 확인 | 3단계 이후 |
| V10 | 동적 OFF | 정적 대체만 제공, 동적 경로·외부 호출·작업 시작 없음 | 3단계 이후 |
| V11 | 동적 ON 및 전환 | 구현한 기능의 실행·중단, 실행 중 작업·저장 데이터 처리 | 6단계 |
| V12 | 플러그인 환경 제한 | 미지원 플랫폼·모드에서 실행 차단, 데이터 보존 | 3단계 이후 |
| V13 | 입력·열기·저장 성능 | 정한 문서·기기·측정 조건별 목표와 제한 기록 | 2단계 이후 |

- [ ] V01~V08을 실행할 최소 절차와 자료를 정하고 필요한 항목을 1단계·2단계 작업으로 옮긴다.
- [ ] V09~V12의 관찰 방법과 예제 기능을 정의하되 서버·격리·전체 플러그인 시스템을 0단계에서 구현하지 않는다.
- [ ] 테스트마다 결과를 `미실행 / 통과 / 부분 통과 / 실패`로 기록하고 실제 검증 근거가 생긴 항목만 완료 처리한다.

### 성능과 데이터의 판단 기준

- [ ] 필수 조건: 저장 완료한 지원 문서의 원본 보존, 미지원 확장 보존, 로컬 기본 흐름의 계정·온라인 의존성 제거를 정한다.
- [ ] 필수 조건: 동적 OFF에서는 비활성 기능의 동적 요청·주기 작업이 실행되지 않아야 한다. 정적 자산·검색 인덱스를 읽는 요청과 구분한다.
- [ ] 성능 목표: 문서 열기 `___ms`, 입력 반영 `___ms`, 필기 반영 `___ms`, 저장 완료 `___ms`, 메모리·결과물 크기 `___`를 기기·문서별로 정한다.
- [ ] 측정 조건: 시작·종료 지점, cold/warm 실행, 반복 횟수, p95 등 집계 방식, 기기·빌드 설정을 기록한다.
- [ ] 입력·필기 지연은 측정 도구·프레임 기록·기기 조건으로 확인한다. 사용 소개 영상만으로 정밀 지연 수치를 입증하지 않는다.
- [ ] 성능이 목표에 못 미치면 기능 범위·표시 방식·데이터 구조·후보 전환 중 무엇을 재검토할지 정한다.

## 7. 장비·기록·녹화 준비

- [ ] 첫 iPad 기기·펜·키보드·OS와 실기기 설치 경로를 기록하거나 확보 계획·확인 시점을 정한다.
- [ ] 첫 Android 태블릿·펜·키보드·OS·WebView 및 개발 도구 환경을 기록하거나 확보 계획을 정한다.
- [ ] 첫 웹 검증 브라우저와 버전을 정하고 Safari·Chromium 계열 등 확대 계획을 구분한다.
- [ ] 시뮬레이터·에뮬레이터·실기기 결과를 따로 기록한다. 미확보 기기는 미검증으로 남긴다.
- [ ] 기능·환경·버전·입력 순서·기대/실제 결과·제한·영상 경로를 함께 남길 위치를 정한다.
- [ ] 테스트 중 기능 설명·설정·사용·조작·결과를 녹화하는 방식을 정한다. 플랫폼별 구간을 식별할 수 있어야 한다.
- [ ] 공개 전 마켓플레이스 영상 업로드·편집·심사 기준을 따르도록 기록 형식을 맞춘다. 0단계에서 마켓플레이스나 영상 업로드 서비스를 만들 필요는 없다.

기기 선정과 기록 양식은 [테스트 환경 문서](테스트%20기기.md)를 따른다. 플랫폼 호환 태그는 검증·영상·심사를 마친 범위에만 부여한다.

## 8. 결정 기록 양식

각 D/T 항목을 결정할 때 아래 양식을 복사해 채운다. 아직 선택하지 않은 상태는 미결정, 프로토타입용 가설은 잠정 선택으로 구분한다.

```text
결정 ID / 항목:

잠정 선택과 비교 후보:
선택 이유와 필요한 가정:
관련 버전·공식 문서 확인일:
범위에서 제외하는 항목:
검증 ID·자료·환경·절차:
현재 결과·근거·영상: 미실행 또는 실제 기록
재검토 조건:
확인할 단계와 담당자:
결정일 / 마지막 확인일:
```

## 9. 0단계 완료 체크

- [ ] D01~D04의 초기 구현에 필요한 선택과 남은 가설을 기록했다.
- [ ] T01~T04에서 먼저 시도할 후보·비교 기준·중단/전환 조건을 정했다. 사이트 기반 등 후속 확정 항목은 확인 시점을 명시했다.
- [ ] 대표 문서의 내용·규모·원본 보존 규약과 자료 제작 작업을 정했다.
- [ ] V01~V08의 재현 절차·기대 결과와 장비 확보 계획을 정했다.
- [ ] 성능 목표의 수치·측정 방법을 정하거나, 첫 측정 후 목표를 정할 시점과 임시 판단 기준을 기록했다.
- [ ] V09~V12의 후속 실행 계획을 남기고 동적 OFF·앱 로컬 기능·플러그인 제한의 책임을 구분했다.
- [ ] 결정 기록과 테스트·영상 근거를 저장할 위치를 정했다.
- [ ] 1단계 첫 작업을 `문서 모델·변경 명령·직렬화·보존 테스트`로, 2단계 연결 작업을 `태블릿·웹 최소 흐름 검증`으로 옮길 수 있다.

0단계 완료는 최종 기술 스택·성능·호환 확정이 아니다. 초기 범위와 잠정 선택·실험 계획이 준비되면 [통합 로드맵](ROADMAP.md)의 1단계로 진행하고, 1~2단계의 결과로 가설을 갱신한다.
