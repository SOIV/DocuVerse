# DocuVerse 에디터 코어/어댑터 패키지 전략

이 문서는 독립 에디터 라이브러리의 구조를 다룬다. 이를 사용하는 셀프호스팅 문서 프레임워크의 제품 범위와 모듈 구성은 [프레임워크 문서](../Framework/README.md)를 참고한다. 아래 플랫폼별 패키지 후보는 공식 앱의 해당 플랫폼 출시를 확정하는 목록이 아니다.

패키지 이름·CLI·코드·의존성 선언은 배포 전 설계 예시다. 정식 이름과 지원 버전·초기 UI 기술은 실제 검증 후 확정한다. 라이선스 상태는 [공통 문서](../README.md)를 따른다.

## 1. 기본 방향

DocuVerse 에디터는 모든 플랫폼에서 동일한 UI 코드를 그대로 공유하는 방식이 아니라, 공통 코어와 플랫폼별 어댑터를 분리하는 구조로 설계한다.

```text
공통 Editor Core
+
프레임워크/플랫폼별 Adapter
+
설치 및 초기 설정 CLI
```

이 구조의 목표는 다음과 같다.

- 문서 모델·명령어·직렬화 규약을 공유하고 파서·협업 연결 등 선택 기능은 독립 모듈로 구성한다.
- React, Vue, Svelte, WebView, Native App 등 환경 차이는 어댑터에서 처리한다.
- 설치 경험은 단순하게 만들되, 내부 구조는 장기적으로 확장 가능하게 유지한다.
- 프레임워크 버전, 런타임, OS 차이로 인한 의존성 문제를 코어에 섞지 않는다.

## 2. 전체 패키지 구조

다음은 역할별 분리 후보이며 모두를 초기 구현하거나 한 번에 설치한다는 의미는 아니다. 첫 편집 어댑터는 태블릿·웹 검증 결과로 선택한다.

```text
@docuverse/editor-core
@docuverse/editor-react
@docuverse/editor-web
@docuverse/editor-webview
@docuverse/editor-cli
```

장기적으로는 다음 패키지로 확장할 수 있다.

```text
@docuverse/editor-vue
@docuverse/editor-svelte
@docuverse/editor-android
@docuverse/editor-ios
@docuverse/editor-tauri
@docuverse/editor-electron
@docuverse/editor-native-bridge
```

패키지 책임은 명확히 분리한다.

| 패키지 | 역할 |
| --- | --- |
| `@docuverse/editor-core` | 문서 모델, 스키마, 명령어, selection, history, 직렬화·파서 연결 규약, plugin API |
| `@docuverse/editor-react` | 선택 시 React 환경의 컴포넌트, hook, event binding |
| `@docuverse/editor-vue` | 선택 시 검증한 Vue 버전의 컴포넌트와 상태 연결 |
| `@docuverse/editor-svelte` | 선택 시 검증한 Svelte 환경의 component/action/store 연결 |
| `@docuverse/editor-web` | 프레임워크 독립 웹 런타임, DOM binding, browser utility |
| `@docuverse/editor-webview` | Android WebView, iOS WKWebView, desktop WebView bridge |
| `@docuverse/editor-native-bridge` | native app과 editor core/webview 사이의 message protocol |
| `@docuverse/editor-cli` | 프로젝트 환경 감지, adapter 설치, 설정 파일 생성 |

## 3. Editor Core의 범위

코어는 특정 UI 프레임워크에 의존하지 않는다. React, Vue, Svelte, Next.js, SvelteKit, Android, iOS, Electron, Tauri 같은 구체 환경의 API가 코어에 들어가면 안 된다.

필수 코어의 책임은 다음과 같다.

- 문서 모델
- 노드/마크 스키마
- 명령어 시스템
- selection 상태 모델
- undo/redo history
- 플러그인 시스템
- 문서 변경 delta
- 스키마 버전·미지원 확장 데이터 보존 규약
- 공통 HTML·URL 허용 정책
- 테스트 가능한 순수 로직

Markdown·나무위키 스타일 파서, HTML import/export 처리, 고급 표·수식과 협업 데이터 연결은 공통 규약을 사용하는 선택형 모듈로 분리한다. 코어 사용에 모두를 필수 설치하지 않는다. HTML 정제 구현은 실행 환경에 맞춰 연결한다.

코어에 포함하지 않을 항목은 다음과 같다.

- React component
- Vue component
- Svelte component
- DOM 이벤트 직접 처리
- WebView message bridge
- native clipboard API
- OS별 file picker
- platform-specific shortcut 처리
- framework lifecycle 처리
- 파일·계정·워크스페이스 관리
- WebSocket·인증·실시간 협업 서버
- 사이트 라우팅·빌드·동적 실행 모드 관리

## 4. Adapter의 범위

어댑터는 코어를 실제 사용 환경에 연결하는 레이어다.

어댑터가 담당할 항목은 다음과 같다.

- 렌더링 연결
- 입력 이벤트 처리
- IME 처리
- clipboard 처리
- drag and drop
- touch/pen 입력
- shortcut mapping
- framework lifecycle 연결
- editor instance 생성/해제
- toolbar/menu integration
- native bridge message 처리

예를 들어 React adapter는 다음과 같은 형태가 된다.

```ts
import { createEditor } from "@docuverse/editor-core";
import { DocuVerseEditor } from "@docuverse/editor-react";

const editor = createEditor({
  schema: "docuverse-default",
});

export function Page() {
  return <DocuVerseEditor editor={editor} />;
}
```

Svelte adapter를 선택할 경우 다음과 같이 component와 lifecycle을 연결할 수 있다. 아래 문법은 예시이며 실제 버전 지원 범위는 검증 후 선언한다.

```svelte
<script lang="ts">
  import { createEditor } from "@docuverse/editor-core";
  import { DocuVerseEditor } from "@docuverse/editor-svelte";

  const editor = createEditor({
    schema: "docuverse-default",
  });
</script>

<DocuVerseEditor {editor} />
```

## 5. 자동 감지와 설치 전략

프로젝트 환경을 자동으로 인식해서 적절한 adapter를 설치하는 기능은 `postinstall`이 아니라 CLI에서 처리한다.

권장 사용 방식은 다음과 같다.

```bash
npx docuverse-editor init
```

CLI는 프로젝트의 파일과 의존성을 보고 환경을 감지한다.

```text
next.config.* 감지 -> React/Next.js 환경
vite.config.* + vue 감지 -> Vue 환경
svelte.config.* 감지 -> SvelteKit 환경
electron 의존성 감지 -> Electron 환경
src-tauri 감지 -> Tauri 환경
capacitor/cordova 감지 -> WebView 기반 모바일 환경
```

감지 결과에 따라 CLI는 사용자에게 설치할 패키지를 명시적으로 보여준다.

```text
Detected: Next.js
Install:
- @docuverse/editor-core
- @docuverse/editor-react
```

설치는 사용자의 패키지 매니저를 따라간다.

```text
package-lock.json -> npm
pnpm-lock.yaml -> pnpm
yarn.lock -> yarn
bun.lockb 또는 bun.lock -> bun
```

중요한 원칙은 다음과 같다.

- `postinstall`에서 몰래 추가 패키지를 설치하지 않는다.
- lockfile이 예측 가능하게 유지되어야 한다.
- CI 환경에서 같은 결과가 나와야 한다.
- adapter는 사용자가 명시적으로 확인한 뒤 설치한다.
- 자동 감지는 편의 기능이지, 코어 동작의 필수 조건이 아니어야 한다.

## 6. Optional Dependencies 사용 기준

`optionalDependencies`는 framework adapter 자동 설치용으로 사용하지 않는다.

사용 가능한 경우는 다음과 같다.

- OS별 native binary가 필요한 경우
- CPU 아키텍처별 빌드 결과물이 필요한 경우
- WASM/native fallback이 분리되어야 하는 경우
- 플랫폼별 bridge helper가 완전히 선택 기능인 경우

예시는 다음과 같다.

```text
@docuverse/editor-darwin-arm64
@docuverse/editor-darwin-x64
@docuverse/editor-win32-x64
@docuverse/editor-linux-x64
```

UI 어댑터는 OS 바이너리와 책임이 다르므로, 해당 UI 런타임의 peer dependency 선언과 명시적인 CLI 설치를 기준으로 구성한다.

## 7. Peer Dependencies 전략

UI 프레임워크 어댑터는 해당 UI 런타임을 `peerDependencies`로 선언하고, 공통 코어는 내부 의존성으로 연결한다. 불필요한 UI 런타임을 코어나 다른 어댑터에 포함하지 않는다.

| 어댑터 후보 | peer 대상 | 지원 범위 기준 |
| --- | --- | --- |
| React | React·React DOM | 실제 함께 검증한 버전 범위 |
| Vue | Vue | 실제 검증한 버전 범위 |
| Svelte | Svelte 및 필요한 런타임 | 실제 검증한 버전 범위 |

검증하지 않은 미래 주버전까지 포함하는 무제한 범위를 기본 선언하지 않는다. 내부 workspace 의존성은 배포 시 실제 배포 버전과 일치하는지 확인한다. Next.js·SvelteKit 등 별도 어댑터는 기본 UI 어댑터로 해결되지 않는 수명·렌더링 문제가 있을 때 검토한다.

## 8. 버전별 Adapter 분리 기준

다른 버전을 하나의 어댑터에서 안정적으로 지원할 수 있으면 유지하고, 검증 범위·성능·수명 관리의 차이가 커질 때 별도 진입점 또는 패키지를 검토한다. 처음부터 모든 UI 기술·주버전을 동시에 구현하지 않는다.

실제 패키지 지원 범위와 마켓플레이스의 플랫폼 검증 태그는 구분한다. 플러그인 태그는 [공통 검증 정책](../Framework/1.%20framework-runtime-and-plugin-policy.md)에 따라 버전별 근거를 연결한다.

## 9. 단일 Entry Package 전략

사용자 경험을 단순화하기 위해 얇은 entry package를 제공할 수 있다.

```text
@docuverse/editor
```

이 패키지는 core와 adapter를 모두 내장하는 거대한 패키지가 아니라, export 경로를 정리하는 얇은 진입점 역할을 한다.

예시는 다음과 같다.

```json
{
  "name": "@docuverse/editor",
  "exports": {
    ".": "./dist/core/index.js",
    "./react": "./dist/react/index.js",
    "./vue": "./dist/vue/index.js",
    "./svelte": "./dist/svelte/index.js",
    "./webview": "./dist/webview/index.js"
  }
}
```

사용 예시는 다음과 같다.

```ts
import { createEditor } from "@docuverse/editor";
import { DocuVerseEditor } from "@docuverse/editor/react";
```

이 방식은 import 경로가 깔끔하다는 장점이 있다. 다만 내부 패키지 경계와 release 관리가 흐려질 수 있으므로, 초기에는 개별 패키지 구조를 먼저 안정화한 뒤 도입하는 것이 좋다.

## 10. 태블릿·웹 및 후속 플랫폼 전략

iPadOS·Android 태블릿 편집과 웹 문서 표시를 초기 검증 대상으로 둔다. WebView, 네이티브 UI, 공통 웹 편집 계층은 후보이며 하나를 확정 전제로 두지 않는다.

| 후보 | 확인할 사항 |
| --- | --- |
| WebView 기반 편집 | 편집 로직 재사용, IME·선택·터치·펜·클립보드·접근성·성능 |
| 네이티브 입력·표시 | 공통 모델 연결, 플랫폼 UI·필기 품질, bridge 비용 |
| 웹 읽기 전용 렌더러 | 편집 UI·서버 없이 사용, 정적 출력·미지원 블록 대체 |
| 웹 편집 어댑터 | 제공할 경우 해당 브라우저의 입력·선택·호스트 수명 |

Windows·macOS 공식 앱 제공 여부는 미정이다. Electron·Tauri·WebView2 등 패키지 후보와 Linux 대응은 후속 수요·검증에 따라 검토한다. 네이티브 어댑터나 WASM/Rust 기반 검토도 필요성이 확인된 범위에서 진행한다.

## 11. 권장 개발 순서

1. 공통 모델·최소 코어와 타입·확장 규약을 정의한다.
2. 대표 문서를 태블릿 편집 환경과 웹 읽기 전용 표시에서 검증하고 첫 어댑터를 선택한다.
3. 편집·표시·파서 진입점을 분리하고 필요한 경우 WebView·네이티브 bridge를 구성한다.
4. CLI와 예제에서 실제 선택한 어댑터만 설치·설정하도록 한다.
5. 앱·프레임워크의 실제 사용을 검증하면서 추가 UI·플랫폼 어댑터를 확장한다.

기능 단계의 완료 기준은 [에디터 로드맵](editor-library_roadmap.md)에서 관리한다. 프레임워크의 사이트 생성 도구와 에디터 설치 CLI는 책임을 구분하고, 에디터 CLI가 사이트 서버·인증까지 자동 구성하지 않는다.

## 12. 의존성과 배포 원칙

- 코어는 특정 UI 프레임워크·DOM·OS·서버에 독립적인 규약과 로직을 유지한다.
- 어댑터는 플랫폼 차이를 처리하고 선택형 기능은 별도 모듈·진입점으로 제공한다.
- CLI는 명시적인 환경 감지·설치를 보조하며 `postinstall`에서 임의 설치하지 않는다.
- optional dependencies는 OS·CPU·네이티브 바이너리 등 필요한 범위에 제한하고 UI 어댑터는 peer dependencies로 관리한다.
- 읽기 전용 사이트에서 편집 UI·협업 서버를 필수로 설치하지 않는 구성을 검증한다.
- 지원 플랫폼·버전은 실제 테스트와 기록을 바탕으로 선언한다.
