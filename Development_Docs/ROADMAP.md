# DocuVerse 통합 개발 로드맵

독립 에디터 라이브러리, 공식 태블릿 앱, 셀프호스팅 문서 프레임워크의 개발 순서와 선행 조건을 하나로 관리한다. 제품별 문서는 상세 기능·검증 기준을 담당하고, 제품 간 우선순위·분기·배포 판단은 이 문서를 기준으로 한다.

현재는 기획·설계 문서를 정리한 상태이며 아래 구현 단계가 완료되었다는 의미는 아니다. 개발 기간과 출시 날짜는 인력·기술·기기 검증 범위를 확인한 뒤 산정한다.

## 1. 전체 순서

```text
0. 초기 범위·검증 조건 정리
  → 1. 공통 문서 모델·최소 에디터
  → 2. 태블릿 입력·저장과 웹 표시를 같은 문서로 검증
  → 3. 최소 확장 규약·플랫폼 경계·실행 모드 제어
      ├─ 4A. 태블릿 로컬 MVP → 5. 앱·관련 라이브러리의 첫 배포 판단
      └─ 4B. 정적 프레임워크 MVP → 5. 프레임워크·관련 라이브러리의 첫 배포 판단
          공통 기반을 충족한 제품부터 독립적으로 배포 가능

3·4의 검증된 기반 → 6. 대표 동적 기능·선택형 온라인 서비스
                 → 7. API 커넥터·고급 문서 기능·협업을 필요별 확장
검증된 SDK·배포·영상 기록 → 8. 마켓플레이스 운영·추가 환경 검토
```

앱과 프레임워크는 최소 에디터를 실제로 사용하면서 함께 검증한다. 공통 데이터·입력·저장 문제가 확인되면 기능을 더 붙이기 전에 기반을 보완한다.

4A와 4B는 서로의 완성을 요구하지 않는 개발 갈래다. 한 사람이 진행한다면 아래 권장 작업 순서에 따라 번갈아 검증할 수 있다.

## 2. 단계별 결과와 완료 기준

| 단계 | 우선 작업 | 결과물 | 다음 단계로 넘어갈 기준 |
| --- | --- | --- | --- |
| 0. 범위·검증 조건 | 대표 문서, 최소 블록, 기기·입력·성능 확인 항목, 기술 후보 선정 | 초기 범위·비교 항목·결정 기록 | 무엇을 구현·검증하고 무엇을 미룰지 명시, 필요한 실제 테스트 환경 확보 계획 |
| 1. 공통 기반 | 문서·블록 ID, 스키마 버전·확장 데이터, 명령·선택·history, 직렬화 | 최소 코어와 대표 문서 자료 | 생성·변경·저장·재열기에서 데이터 보존, UI·서버 없이 문서 로직 검증 |
| 2. 실제 사용 경로 | iPadOS·Android 입력·저장 프로토타입, 웹 읽기 전용 표시 | 같은 문서를 편집·저장·웹에서 보는 최소 예제 | IME·선택·터치·기본 펜·저장 복원 검증, 편집 엔진·UI·어댑터 선택 근거 확보 |
| 3. 확장·실행 경계 | 스키마·명령·표시 등록, 필요한 환경·권한, 시작·중단, 사이트 모드 선택·저장 | 예제 확장과 최소 호스트 규약 | 미지원 환경에서 실행 차단·데이터 보존, OFF에서 정적 대체만 작동하고 동적 경로는 실행되지 않음 |
| 4A. 앱 로컬 MVP | 태블릿 문서 탐색·편집·필기·검색·태그·백링크·가져오기·내보내기 | 서버·계정 없이 쓰는 하이브리드 노트 앱 | 지원하려는 각 태블릿 환경에서 기본 사용 흐름과 재시작·원본 보존 검증 |
| 4B. 정적 프레임워크 MVP | 사이트 초기 구성, 렌더러·탐색·테마·링크·정적 검색·빌드 | 직접 호스팅하는 문서 사이트와 렌더러 단독 예제 | 동적 서버 없이 배포 가능, 첫 구동 모드 설정·정적 대체·미지원 기능 차단 확인 |
| 5. 첫 배포 판단 | 제품별 설치·타입·문서·버전·라이선스·지원 범위, 실제 사용 피드백 | 준비된 에디터 패키지·앱·프레임워크의 초기 배포 | 각 배포물의 필수 범위와 검증 근거 확보, 별도 프로젝트에서 재현 가능 |
| 6. 최소 동적·온라인 기능 | 대표 동적 기능 한 개, 필요한 인증·권한·저장소·공개 API 연결 | 선택적으로 켜서 사용하는 최소 서버 기능 | ON에서 기능 사용, OFF에서 실행 경로·작업 중단, 재시작·모드 전환에서 데이터 보존 |
| 7. 선택형 확장 | 외부 API 커넥터, 고급 문법·표·수식, 협업·백업 등 | 기능별 공식 모듈·플러그인과 지원 기록 | 해당 기능의 선행 조건 충족, 플랫폼·모드별 정상 작동·제한·변환 범위 확인 |
| 8. 생태계·후속 환경 | SDK·템플릿, 영상 업로드·심사·호환 태그, 업데이트·배포 운영 | 공개 가능한 마켓플레이스와 후속 지원 계획 | 제출 버전과 영상·환경 연결, 공개 전 심사·거부·보완 요청·태그 관리 검증 |

단계 5는 모든 제품이 한꺼번에 통과해야 하는 관문이 아니라 배포물별 점검이다. 단계 6~8의 모든 기능을 마쳐야 에디터나 로컬 앱·정적 프레임워크를 배포할 수 있는 것은 아니다. 반대로 초기 배포가 끝나지 않았더라도 필요한 기반이 검증되었다면 별도 갈래의 기술 검증은 진행할 수 있다.

## 3. 처음 착수할 작업

### 0단계: 비교할 범위를 먼저 고정

결정 항목·기술 후보·대표 문서·검증 계획·완료 판단은 [0단계 체크리스트](STAGE_0_CHECKLIST.md)에서 관리한다. 이 단계에서는 잠정 선택과 실험 계획을 준비하며, 실제 입력·저장·표시 결과는 1~2단계에서 검증한다.

- 대표 문서에 문단·제목·목록·기본 서식, 이미지·첨부 참조, 단순 필기·도형, 미지원 확장 블록을 포함한다.
- 문서 크기·입력 반응성·저장 복원 등 실제로 확인할 조건을 정한다. 아직 측정하지 않은 수치를 달성한 것으로 기록하지 않는다.
- 최소 문서 저장 표현과 텍스트 형식 내보내기를 구분한다. 필기·고급 블록의 원본 보존 경로를 정한다.
- 편집 엔진·태블릿 UI·웹 표시 후보를 좁히고 플랫폼별 실제 테스트 방법과 필요한 기기를 정한다.
- 패키지 경계는 책임 중심으로 설계하고 초기부터 모든 UI 어댑터·배포 환경을 구현하지 않는다.

### 1~2단계: 한 문서의 전체 흐름 확인

첫 실행 가능한 목표는 **태블릿에서 대표 문서 작성 → 로컬 저장 → 앱 재시작 후 재열기 → 명시적 내보내기 → 웹 렌더러에서 표시**다.

한 태블릿 환경에서 먼저 연결한 뒤 다른 우선 대상 태블릿 환경에서 같은 흐름을 검증할 수 있다. 첫 환경의 성공만으로 나머지 환경의 지원을 주장하지 않는다. 두 환경의 입력·펜·저장 결과와 웹 표시를 확인한 뒤 구현 방식의 선택 근거를 남긴다.

이 단계의 앱은 제품 MVP 전체가 아니라 검증용 최소 화면이다. 웹도 사이트 프레임워크 전체가 아니라 읽기 전용 렌더러 예제부터 시작한다. 계정·클라우드·실시간 협업·마켓플레이스는 이 검증에 필수로 요구하지 않는다.

### 3단계: 제품을 키우기 전 확장 경계 확인

공개 인터페이스만 사용하는 작은 블록·계산 확장 하나를 만들고, 공통 데이터·로직과 환경별 표시를 나눈다. 앱 전용 기능이나 웹 전용 기능은 상대 환경에서 실행되지 않아도 원본이 보존되어야 한다.

사이트는 첫 구성·구동 시 동적 기능 ON/OFF를 선택·저장하도록 한다. 이때의 ON은 실행을 허용하는 설정이며 아직 구현하지 않은 서버 기능이 제공된다는 뜻은 아니다. 단계 6에서 실제 동적 기능을 연결할 때 ON 동작을 다시 검증한다.

정적 대체가 있는 예제와 없는 예제를 확인하고, 기능 해제·호스트 종료 시 실행 수명을 정리한다. 초기에는 작동 여부를 확인하는 제한된 예제를 사용하며, 외부 커뮤니티 코드를 공개 실행하기 전에는 필요한 권한 강제·격리 방식을 검증한다.

## 4. 로컬 앱과 정적 사이트의 개발 분기

### 4A. 태블릿 앱

텍스트·필기·컬러 블록·포스트잇·도형의 기본 경험, 로컬 문서 탐색·저장·검색·태그·백링크를 구현한다. 계정·네트워크 없이 기본 작업이 가능해야 한다.

가져오기·내보내기와 미지원 블록의 원본 보존을 확인하고, 앱 중단·재시작·파일 권한 변화에서 문서가 복원되는지 검증한다. 플랫폼별 세부 범위는 [앱 로드맵](Application/05b_roadmap_and_future.md)을 따른다.

### 4B. 셀프호스팅 정적 프레임워크

대표 문서를 가져와 페이지·문서 트리·내부 링크·테마·사전 생성 검색 인덱스로 구성한다. 정적 출력은 운영자가 선택한 호스팅 환경에서 동적 서버 없이 제공할 수 있어야 한다.

사이트 전체와 별개로 렌더러·문서 처리 기능만 기존 웹 프로젝트에서 사용하는 예제도 만든다. 앱 완성본 없이 단계 2의 문서 자료를 이용해 진행할 수 있다. 세부 범위는 [프레임워크 로드맵](Framework/03_scope_and_roadmap.md)을 따른다.

### 인력이 적을 때의 권장 순서

1. 단계 2에서 태블릿 편집·저장·웹 표시의 얇은 사용 경로를 모두 연결한다.
2. 단계 3의 최소 확장·실행 모드 경계를 검증한다.
3. 핵심 제품 경험인 4A 로컬 앱을 우선 완성한다.
4. 그 문서를 이용해 4B 사이트 구성과 정적 게시를 완성한다. 웹 표시 검증 자체는 이미 단계 2에서 수행한다.
5. 준비된 제품부터 단계 5의 배포 기준을 확인하고 피드백을 받는다.

4A·4B의 작업량이나 사용성 검증 결과에 따라 순서를 바꿀 수 있다. 어느 경우에도 전체 고급 에디터·협업 기능이 끝날 때까지 정적 게시를 미루지 않는다.

## 5. 이후 확장의 선행 조건

단계 7의 항목은 모두를 순서대로 구현하는 필수 묶음이 아니다. 실제로 채택하는 기능의 선행 조건을 확인해 별도로 진행한다.

| 확장 갈래 | 먼저 필요한 기반 | 개발·검증 방향 |
| --- | --- | --- |
| 웹 동적 기능 | 단계 3의 실행 제어와 검증된 사이트 기반 | 단계 6에서 기능 하나의 인증·저장·권한·ON/OFF 확인 후 확대 |
| 외부 API 커넥터 | 확장 규약, 해당 호스트의 인증·비밀키 보관·네트워크 실행 | 서비스 하나로 동작·취소·오류·요청 제한 확인, 제공 시 정적 스냅샷도 별도 검증 |
| 고급 문법·표·수식 | 안정된 문서·변환·확장 규약 | 로컬 계산·읽기 전용 표시부터 구현 가능, 동적 서버 완성을 기다리지 않음 |
| 앱 외부 저장소·백업 | 로컬 저장·복원과 플랫폼별 파일·권한 처리 | 검증한 외부 저장소부터 확장, 공식 클라우드와 구분 |
| 공식 클라우드·동적 공유 | 문서 저장·전송 규약, 필요한 서버·인증·권한 | 앱과 사이트가 재사용할 경계를 검증, 공식 서비스 한도는 별도 정책 적용 |
| 실시간 협업 | 문서 변경·선택형 협업 데이터 연결, 통신·권한·저장·재연결 | 로컬 편집 독립성·동시 변경·오프라인 복귀를 확인한 뒤 제공 |
| 공개 API·웹훅·자동화 | 대상 기능의 권한·실행 경로와 이벤트 수명 | 필요한 조회·변경 경로부터 제공, OFF에서 해당 동적 처리가 중단되는지 확인 |
| 추가 UI·플랫폼 | 재사용할 코어·SDK, 해당 환경의 실제 검증 자원 | 수요가 확인된 환경부터 선택, 기능별 지원 범위와 영상 기록 |

앱용 API 커넥터는 해당 앱의 실행·인증 조건을 충족하면 개발할 수 있으며 셀프호스팅 서버 전체에 종속시키지 않는다. 정적 스냅샷은 명시적인 빌드·내보내기 단계에서 생성하고, 동적 OFF 상태의 페이지 열기가 외부 서비스 호출을 시작하지 않도록 한다.

실시간 협업·클라우드·AI는 기본 로컬 앱·정적 사이트 출시의 필수 조건이 아니다. 반면 해당 기능을 실제 제공할 때 필요한 인증·권한·오류 처리·호환 검증은 후속으로 미루지 않는다.

## 6. 첫 배포와 마켓플레이스의 구분

| 배포 대상 | 최소 판단 기준 |
| --- | --- |
| 독립 에디터 패키지 | 선언한 코어·어댑터·변환 기능의 테스트, 독립 통합 예제·타입·문서, 버전·라이선스·지원 범위 |
| 공식 태블릿 앱 | 해당 플랫폼의 로컬 MVP·입력·저장 복원, 문서 보존, 설치·사용 안내 |
| 정적 프레임워크 | 사이트 생성·문서 게시·정적 배포, 첫 구동 설정, OFF 동작, 렌더러 단독 사용·문서 |
| 동적 모듈·공식 커넥터 | 해당 환경의 설정·권한·실제 동작·중단, 지원 모드와 정적 대체의 검증 |
| 마켓플레이스 | SDK·배포 운영, 플랫폼별 영상 업로드·공개 전 심사·호환 태그·업데이트 검증 |

초기 배포는 공개 SDK·예제·검증된 공식 패키지부터 가능하다. 마켓플레이스 공개는 영상 업로드와 심사 절차까지 준비된 별도 단계이며, 초기 배포와 동시에 시작할 필요는 없다.

에디터의 첫 배포에 모든 나무위키 스타일 문법·고급 표·협업을 요구하지 않는다. 제공 범위를 명시하고 실제 검증된 기능·환경만 지원으로 표시한다. 앱·프레임워크도 각 배포물의 범위에 필요한 의존성과 검사만 충족하면 독립적으로 배포할 수 있다.

## 7. 전 단계에서 남길 근거

- 문서 스키마·기술·어댑터 선택과 변경 이유
- 기능·플랫폼·OS·기기·호스트·플러그인 버전별 테스트 결과
- 정적·동적 모드, 필요한 권한·서비스, 미지원 범위와 데이터 보존 결과
- 기능 설명·설정·사용 절차·실제 조작·결과를 포함한 플랫폼별 녹화
- 배포물의 설치·변환 손실·복구·지원 범위와 알려진 제한

테스트와 녹화는 마켓플레이스 구현 단계까지 미루지 않고 실제 기능을 검증할 때부터 남긴다. 영상 제출·편집 허용·공개 전 심사·등록 거부 및 태그 부여 기준은 [공통 정책](Framework/1.%20framework-runtime-and-plugin-policy.md)을 따른다. 환경 선정과 기록 항목은 [테스트 환경](테스트%20기기.md)을 따른다.

## 9. 초기 개발에서 보류하는 범위

모든 UI 어댑터·플랫폼·외부 서비스를 한꺼번에 지원하거나, 모든 동적 기능을 자동으로 정적으로 변환하는 목표는 초기 범위에 넣지 않는다. 전체 IDE·고급 AI·기업 관리·결제·구독 및 광범위한 OS 통합은 기존 제품별 보류 목록에 따라 검토한다.

Windows·macOS 앱 제공 여부는 미정이다. 추가 환경과 기능은 최소 제품의 검증·사용 피드백·유지보수 여력을 확인한 뒤 채택한다. 라이선스·정식 패키지·운영 정책의 미결정 사항도 [공통 문서](README.md)와 해당 제품 문서에 따라 출시 전에 확정한다.
