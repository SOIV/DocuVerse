# DocuVerse 에디터 코어/어댑터 패키지 전략

## 1. 기본 방향

DocuVerse 에디터는 모든 플랫폼에서 동일한 UI 코드를 그대로 공유하는 방식이 아니라, 공통 코어와 플랫폼별 어댑터를 분리하는 구조로 설계한다.

```text
공통 Editor Core
+
프레임워크/플랫폼별 Adapter
+
설치 및 초기 설정 CLI
```

이 구조의 목표는 다음과 같다.

- 문서 모델, 명령어, 파서, 협업, 직렬화 같은 핵심 로직은 하나의 코어에서 공유한다.
- React, Vue, Svelte, WebView, Native App 등 환경 차이는 어댑터에서 처리한다.
- 설치 경험은 단순하게 만들되, 내부 구조는 장기적으로 확장 가능하게 유지한다.
- 프레임워크 버전, 런타임, OS 차이로 인한 의존성 문제를 코어에 섞지 않는다.

## 2. 전체 패키지 구조

초기 구조는 다음과 같이 구성한다.

```text
@docuverse/editor-core
@docuverse/editor-react
@docuverse/editor-web
@docuverse/editor-webview
@docuverse/editor-cli
```

장기적으로는 다음 패키지로 확장할 수 있다.

```text
@docuverse/editor-vue
@docuverse/editor-svelte
@docuverse/editor-android
@docuverse/editor-ios
@docuverse/editor-tauri
@docuverse/editor-electron
@docuverse/editor-native-bridge
```

패키지 책임은 명확히 분리한다.

| 패키지 | 역할 |
| --- | --- |
| `@docuverse/editor-core` | 문서 모델, 스키마, 명령어, selection, history, parser, serializer, plugin API |
| `@docuverse/editor-react` | React/Next.js에서 사용하는 컴포넌트, hook, event binding |
| `@docuverse/editor-vue` | Vue 3용 컴포넌트와 상태 연결 |
| `@docuverse/editor-svelte` | Svelte 5/SvelteKit용 component/action/store 연결 |
| `@docuverse/editor-web` | 프레임워크 독립 웹 런타임, DOM binding, browser utility |
| `@docuverse/editor-webview` | Android WebView, iOS WKWebView, desktop WebView bridge |
| `@docuverse/editor-native-bridge` | native app과 editor core/webview 사이의 message protocol |
| `@docuverse/editor-cli` | 프로젝트 환경 감지, adapter 설치, 설정 파일 생성 |

## 3. Editor Core의 범위

코어는 특정 UI 프레임워크에 의존하지 않는다. React, Vue, Svelte, Next.js, SvelteKit, Android, iOS, Electron, Tauri 같은 구체 환경의 API가 코어에 들어가면 안 된다.

코어에 포함할 항목은 다음과 같다.

- 문서 모델
- 노드/마크 스키마
- 명령어 시스템
- selection 상태 모델
- undo/redo history
- 플러그인 시스템
- Markdown parser/serializer
- 나무위키 문법 parser/serializer
- HTML import/export
- 보안 필터링 정책
- 협업 데이터 모델
- 문서 변경 delta
- 테스트 가능한 순수 로직

코어에 포함하지 않을 항목은 다음과 같다.

- React component
- Vue component
- Svelte component
- DOM 이벤트 직접 처리
- WebView message bridge
- native clipboard API
- OS별 file picker
- platform-specific shortcut 처리
- framework lifecycle 처리

## 4. Adapter의 범위

어댑터는 코어를 실제 사용 환경에 연결하는 레이어다.

어댑터가 담당할 항목은 다음과 같다.

- 렌더링 연결
- 입력 이벤트 처리
- IME 처리
- clipboard 처리
- drag and drop
- touch/pen 입력
- shortcut mapping
- framework lifecycle 연결
- editor instance 생성/해제
- toolbar/menu integration
- native bridge message 처리

예를 들어 React adapter는 다음과 같은 형태가 된다.

```ts
import { createEditor } from "@docuverse/editor-core";
import { DocuVerseEditor } from "@docuverse/editor-react";

const editor = createEditor({
  schema: "docuverse-default",
});

export function Page() {
  return <DocuVerseEditor editor={editor} />;
}
```

Svelte adapter는 Svelte 5 구조에 맞춰 component, action, store를 제공할 수 있다.

```svelte
<script lang="ts">
  import { createEditor } from "@docuverse/editor-core";
  import { DocuVerseEditor } from "@docuverse/editor-svelte";

  const editor = createEditor({
    schema: "docuverse-default",
  });
</script>

<DocuVerseEditor {editor} />
```

## 5. 자동 감지와 설치 전략

프로젝트 환경을 자동으로 인식해서 적절한 adapter를 설치하는 기능은 `postinstall`이 아니라 CLI에서 처리한다.

권장 사용 방식은 다음과 같다.

```bash
npx docuverse-editor init
```

CLI는 프로젝트의 파일과 의존성을 보고 환경을 감지한다.

```text
next.config.* 감지 -> React/Next.js 환경
vite.config.* + vue 감지 -> Vue 환경
svelte.config.* 감지 -> SvelteKit 환경
electron 의존성 감지 -> Electron 환경
src-tauri 감지 -> Tauri 환경
capacitor/cordova 감지 -> WebView 기반 모바일 환경
```

감지 결과에 따라 CLI는 사용자에게 설치할 패키지를 명시적으로 보여준다.

```text
Detected: Next.js
Install:
- @docuverse/editor-core
- @docuverse/editor-react
```

설치는 사용자의 패키지 매니저를 따라간다.

```text
package-lock.json -> npm
pnpm-lock.yaml -> pnpm
yarn.lock -> yarn
bun.lockb 또는 bun.lock -> bun
```

중요한 원칙은 다음과 같다.

- `postinstall`에서 몰래 추가 패키지를 설치하지 않는다.
- lockfile이 예측 가능하게 유지되어야 한다.
- CI 환경에서 같은 결과가 나와야 한다.
- adapter는 사용자가 명시적으로 확인한 뒤 설치한다.
- 자동 감지는 편의 기능이지, 코어 동작의 필수 조건이 아니어야 한다.

## 6. Optional Dependencies 사용 기준

`optionalDependencies`는 framework adapter 자동 설치용으로 사용하지 않는다.

사용 가능한 경우는 다음과 같다.

- OS별 native binary가 필요한 경우
- CPU 아키텍처별 빌드 결과물이 필요한 경우
- WASM/native fallback이 분리되어야 하는 경우
- 플랫폼별 bridge helper가 완전히 선택 기능인 경우

예시는 다음과 같다.

```text
@docuverse/editor-darwin-arm64
@docuverse/editor-darwin-x64
@docuverse/editor-win32-x64
@docuverse/editor-linux-x64
```

이 방식은 `esbuild`, `sharp`, `@next/swc` 같은 패키지에서 사용하는 방식과 유사하다. 다만 DocuVerse의 React/Vue/Svelte adapter는 OS binary가 아니므로 optional dependency보다 peer dependency와 CLI 설치가 더 적합하다.

## 7. Peer Dependencies 전략

프레임워크 adapter는 해당 프레임워크를 `peerDependencies`로 둔다.

예를 들어 React adapter는 다음과 같은 구조가 된다.

```json
{
  "name": "@docuverse/editor-react",
  "peerDependencies": {
    "react": ">=18",
    "react-dom": ">=18"
  },
  "dependencies": {
    "@docuverse/editor-core": "workspace:*"
  }
}
```

Svelte adapter는 다음과 같다.

```json
{
  "name": "@docuverse/editor-svelte",
  "peerDependencies": {
    "svelte": ">=5"
  },
  "dependencies": {
    "@docuverse/editor-core": "workspace:*"
  }
}
```

Next.js, SvelteKit 같은 메타 프레임워크는 별도 adapter가 꼭 필요할 때만 분리한다. 단순히 React 또는 Svelte adapter로 충분하다면 별도 패키지를 만들지 않는다.

## 8. 버전별 Adapter 분리 기준

처음부터 버전별 패키지를 과하게 나누지 않는다.

기본 원칙은 다음과 같다.

- React 18과 React 19를 하나의 adapter에서 안정적으로 지원할 수 있으면 `@docuverse/editor-react` 하나로 유지한다.
- 호환성 코드가 복잡해지고 bundle size나 lifecycle 문제가 커지면 버전별 entry 또는 패키지로 분리한다.
- Vue는 Vue 3만 대상으로 시작한다.
- Svelte는 Svelte 5를 기준으로 시작한다.

필요할 경우 다음처럼 entry를 나눌 수 있다.

```text
@docuverse/editor-react
@docuverse/editor-react/react18
@docuverse/editor-react/react19
```

또는 패키지 자체를 분리할 수 있다.

```text
@docuverse/editor-react18
@docuverse/editor-react19
```

다만 패키지 분리는 유지보수 비용이 크므로 마지막 선택지로 둔다.

## 9. 단일 Entry Package 전략

사용자 경험을 단순화하기 위해 얇은 entry package를 제공할 수 있다.

```text
@docuverse/editor
```

이 패키지는 core와 adapter를 모두 내장하는 거대한 패키지가 아니라, export 경로를 정리하는 얇은 진입점 역할을 한다.

예시는 다음과 같다.

```json
{
  "name": "@docuverse/editor",
  "exports": {
    ".": "./dist/core/index.js",
    "./react": "./dist/react/index.js",
    "./vue": "./dist/vue/index.js",
    "./svelte": "./dist/svelte/index.js",
    "./webview": "./dist/webview/index.js"
  }
}
```

사용 예시는 다음과 같다.

```ts
import { createEditor } from "@docuverse/editor";
import { DocuVerseEditor } from "@docuverse/editor/react";
```

이 방식은 import 경로가 깔끔하다는 장점이 있다. 다만 내부 패키지 경계와 release 관리가 흐려질 수 있으므로, 초기에는 개별 패키지 구조를 먼저 안정화한 뒤 도입하는 것이 좋다.

## 10. 모바일/데스크톱 지원 전략

모바일과 데스크톱은 초기에는 WebView 기반으로 접근한다.

```text
Android -> WebView
iOS/iPadOS -> WKWebView
Windows App -> WebView2 또는 Electron/Tauri
macOS App -> WKWebView, Electron, Tauri
```

초기 WebView 기반 전략의 장점은 다음과 같다.

- 웹 에디터 기능을 빠르게 재사용할 수 있다.
- 플랫폼 간 UI 일관성을 유지하기 쉽다.
- 문서 모델과 렌더링 검증 비용이 줄어든다.
- 데스크톱 앱과 모바일 앱의 초기 출시 속도가 빨라진다.

단점은 다음과 같다.

- 네이티브 selection과 IME 품질에 한계가 있을 수 있다.
- 대용량 문서에서 성능 최적화가 필요하다.
- 플랫폼별 clipboard, file, shortcut, accessibility 처리가 필요하다.

따라서 장기적으로는 다음 순서로 확장한다.

```text
1. Web editor 안정화
2. React adapter 우선 제공
3. WebView bridge 제공
4. Electron/Tauri desktop 지원
5. iOS/Android WebView app 지원
6. 필요한 영역만 native bridge 강화
7. 장기적으로 WASM/Rust core 검토
```

## 11. 권장 개발 순서

1단계는 최소 패키지로 시작한다.

```text
@docuverse/editor-core
@docuverse/editor-react
@docuverse/editor-cli
```

2단계에서 웹 공통 유틸과 WebView bridge를 분리한다.

```text
@docuverse/editor-web
@docuverse/editor-webview
@docuverse/editor-native-bridge
```

3단계에서 다른 프레임워크 adapter를 추가한다.

```text
@docuverse/editor-vue
@docuverse/editor-svelte
```

4단계에서 앱 환경을 확장한다.

```text
@docuverse/editor-electron
@docuverse/editor-tauri
@docuverse/editor-android
@docuverse/editor-ios
```

## 12. 결론

DocuVerse 에디터는 코어 하나를 공통으로 만들고, 각 환경은 adapter로 연결하는 구조가 가장 적합하다.

자동 환경 감지는 패키지 설치 후 임의로 동작하는 방식이 아니라, `docuverse-editor init` 같은 명시적인 CLI 명령으로 제공한다. 이렇게 하면 사용자는 간단하게 시작할 수 있고, 프로젝트는 lockfile, CI, 보안 정책 측면에서 예측 가능성을 유지할 수 있다.

핵심 원칙은 다음과 같다.

- core는 framework-agnostic하게 유지한다.
- adapter는 플랫폼과 프레임워크 차이를 흡수한다.
- CLI는 환경 감지와 설치 보조를 담당한다.
- optional dependencies는 OS/CPU/native binary에만 제한적으로 사용한다.
- framework adapter는 peer dependencies로 관리한다.
- 초기에는 React/Web 중심으로 안정화하고, 이후 Vue, Svelte, WebView, Native App으로 확장한다.
